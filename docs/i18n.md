# Translations and RTL

The plugin ships its own translation catalogs in `languages/` and renders right-to-left for Arabic.
This document describes the shipped locales, how the catalogs are loaded, the translator rules and
how to refresh the catalogs.

## Supported locales

| Documented code | WordPress locale | Catalog (`.po` / `.mo`) | Direction |
|---|---|---|---|
| `en-US` (fallback) | `en_US` (and every other `en_*`) | `icc-gg-sign-in-openid-connect-en_US` | LTR |
| `pt-BR` | `pt_BR` | `icc-gg-sign-in-openid-connect-pt_BR` | LTR |
| `es-MX` | `es_MX` | `icc-gg-sign-in-openid-connect-es_MX` | LTR |
| `fr-FR` | `fr_FR` | `icc-gg-sign-in-openid-connect-fr_FR` | LTR |
| `zh-CN` | `zh_CN` | `icc-gg-sign-in-openid-connect-zh_CN` | LTR |
| `hi-IN` | `hi_IN` | `icc-gg-sign-in-openid-connect-hi_IN` | LTR |
| `ar-SA` | `ar` (and every other `ar_*`) | `icc-gg-sign-in-openid-connect-ar` | **RTL** |

`en_US` is an identity catalog: every `msgstr` equals its `msgid`. It exists so English is an
explicit fallback target and so a locale without a catalog keeps the source strings instead of
falling through to an unrelated one.

## Files

```
languages/
├── icc-gg-sign-in-openid-connect.pot           source strings (template, not read at runtime)
├── icc-gg-sign-in-openid-connect-en_US.po/.mo
├── icc-gg-sign-in-openid-connect-pt_BR.po/.mo
├── icc-gg-sign-in-openid-connect-es_MX.po/.mo
├── icc-gg-sign-in-openid-connect-fr_FR.po/.mo
├── icc-gg-sign-in-openid-connect-zh_CN.po/.mo
├── icc-gg-sign-in-openid-connect-hi_IN.po/.mo
└── icc-gg-sign-in-openid-connect-ar.po/.mo
```

Only the `.mo` files are read at runtime; the `.po` files are the editable source and the `.pot`
template is the reference for translators. All three are committed, so a release built from the
repository is translated out of the box.

## How the catalogs are loaded

1. The plugin header declares the text domain and the folder:

   ```php
   * Text Domain:       icc-gg-sign-in-openid-connect
   * Domain Path:       /languages
   ```

   `Domain Path` is what makes WordPress look for a catalog inside the plugin folder.

2. `icc_gg_sign_in_openid_connect_load_textdomain()` runs on `plugins_loaded` priority `5` and
   calls `load_plugin_textdomain()` with a path derived from the plugin basename:

   ```php
   load_plugin_textdomain(
       'icc-gg-sign-in-openid-connect',
       false,
       dirname( ICC_GG_SIGN_IN_OPENID_CONNECT_BASENAME ) . '/languages'
   );
   ```

   Using the basename instead of a hard-coded slug keeps both layouts working: a git clone lands in
   `wp-content/plugins/wordpressiccopenidclient/`, a release install in
   `wp-content/plugins/icc-gg-sign-in-openid-connect/`.

   WordPress only auto-loads language packs installed under `wp-content/languages/plugins`, which is
   why the bundled catalog has to be loaded explicitly. A language pack still wins when the site
   installs one: `load_plugin_textdomain()` prefers the global directory.

3. `icc_gg_sign_in_openid_connect_plugin_locale()` (filter `plugin_locale`) maps the requested
   locale to a shipped catalog:

   | Requested | Returns |
   |---|---|
   | `pt_BR`, `pt-BR`, `es_MX`, `es-MX`, `fr_FR`, `fr-FR`, `zh_CN`, `zh-CN`, `hi_IN`, `hi-IN`, `en_US`, `en-US` | the same locale, normalised to underscores |
   | any other `en_*` (`en_GB`, `en_CA`, `en`) | `en_US` |
   | any `ar*` (`ar`, `ar_SA`, `ar_EG`) | `ar` |
   | anything else (`de_DE`, `pt_PT`, …) | unchanged (English source strings) |

   The filter is global, so it returns `$locale` immediately for any other text domain.

## Right-to-left support

`is_rtl()` follows the **site** locale, which is wrong in the admin: a user whose profile language
is Arabic on an English site would get an LTR admin. `icc_gg_sign_in_openid_connect_is_rtl_locale()`
instead reads the locale that actually drives translations (`determine_locale()`, falling back to
`get_locale()` before WordPress 4.7) and matches `ar`, `fa`, `he`, `ur`, `ckb`, `dv`, `ps`, `sd`,
`ug`, `yi`.

Four behaviours follow from it:

- `language_attributes` appends `dir="rtl"` when core did not already set a direction.
- `admin_body_class` and `login_body_class` add the `rtl` class, so the plugin stylesheets and any
  theme or plugin rules scoped to `.rtl` apply. Core's own RTL stylesheets are still selected from
  `is_rtl()` (the site language), so a per-user Arabic profile on an English site gets the plugin's
  mirrored layout but core's LTR chrome.
- The settings page enqueues `css/styles-admin-rtl.css` after `css/styles-admin.css`; the stylesheet
  right-aligns the logger table, keeps the JSON log payloads left-to-right, mirrors the discovery
  form's accent border and forces the discovery URL field to LTR so URLs stay readable.
- The login screen enqueues `css/styles-login-rtl.css` from `enqueue_login_scripts()`, which moves
  the logo margin of the login button to the left of the text.

RTL detection is independent of the catalog: an `ar_EG` site renders RTL even though it uses the
`ar` catalog, and a right-to-left language the plugin has no catalog for (for example `he_IL`) still
renders RTL with the English strings.

## Using a translated locale

Nothing has to be configured: install the plugin and set **Settings → General → Site Language**, or
**Users → Profile → Language** for a single account, to one of the supported locales.

```bash
wp option update WPLANG pt_BR
wp user meta update admin locale ar
```

## Updating the catalogs

### Source string changed or added

1. Re-extract the template:

   ```bash
   xgettext \
     --language=PHP --from-code=UTF-8 --add-comments=translators: \
     --keyword=__ --keyword=_e --keyword=_x:1,2c --keyword=_n:1,2 --keyword=_nx:1,2,4c \
     --keyword=esc_html__ --keyword=esc_attr__ --keyword=esc_html_e --keyword=esc_attr_e \
     -o /tmp/icc-gg-sign-in-openid-connect.pot \
     icc-gg-sign-in-openid-connect.php includes/*.php
   ```

2. Replace the body of `languages/icc-gg-sign-in-openid-connect.pot` with the new strings, keeping its
   header (charset, `X-Domain`, bug address).
3. Merge the template into each catalog and translate the new entries:

   ```bash
   for po in languages/*.po; do
     msgmerge --update --backup=none "$po" languages/icc-gg-sign-in-openid-connect.pot
   done
   ```

4. Fill in the new `msgstr` values, then rebuild and validate:

   ```bash
   sh tests/build-translations.sh --check-pot
   ```

`msgfmt --statistics` must report every entry as translated — the script fails on `fuzzy`,
`untranslated` or `obsolete` messages and when a catalog is missing an entry the template has.

### Adding a locale

1. Create `languages/icc-gg-sign-in-openid-connect-<locale>.po` (copy an existing catalog and set
   `Language:` plus the correct `Plural-Forms:`).
2. Translate every entry, then run `sh tests/build-translations.sh` to produce the `.mo`.
3. Allow the locale in `icc_gg_sign_in_openid_connect_plugin_locale()` if it is not already reachable
   and add it to the table above.
4. For a right-to-left language, extend the pattern in
   `icc_gg_sign_in_openid_connect_is_rtl_locale()` and add any mirroring the settings page or the
   login button needs to `css/styles-admin-rtl.css` / `css/styles-login-rtl.css`.
5. Add the locale to the `$locales` and `$probes` arrays of `tests/check-translations.php` so the
   catalog is verified in CI and locally.

### Rules for translators

- Keep every placeholder exactly as it appears: `%s`, `%1$s`, `%2$s`, `%d`. `msgfmt --check`,
  `--check-format` and `tests/check-translations.php` reject a translation whose format specifiers or
  HTML tags do not match the source.
- Keep HTML tags (`<strong>`, `</strong>`, `<code>`, `</code>`, `<a …>`, `</a>`) balanced and in the
  same order as the source.
- Never translate protocol names, identifiers or machine-readable values: `OpenID Connect`, `OAuth`,
  `JWT`, `JWKS`, `ID token`, `state`, `scope` values (`openid`, `profile`, `email`), claim keys
  (`preferred_username`, `sub`), option keys, URLs, and the `{email}` / `{displayname}` tokens used by
  the `email_format` and `displayname_format` settings. The plugin feeds those values back to the
  identity provider.
- Keep the leading `ICC.gg` brand untouched.
- The plural entry (`%d field(s) populated`) must use as many forms as the catalog's `Plural-Forms`
  declares: `zh_CN` uses one form (`nplurals=1`), `ar` uses six.
- `en_US` is an identity catalog: regenerate it from the POT instead of translating it.

## Verification

```bash
# Lint, layout and catalogs
find . -name '*.php' -not -path './vendor/*' -exec php -l {} \;
sh tests/validate-plugin-layout.sh
sh tests/build-translations.sh --check-pot
```

`--check-pot` re-runs `xgettext` and fails when the committed template no longer matches the source
strings, which is what happens when a string is edited without refreshing `languages/`.

`tests/check-translations.php` parses the compiled `.mo` files directly, so it needs neither
WordPress nor the locales installed on the machine. It checks that each catalog compiles, that no
`msgstr` is empty, that placeholders and markup survive translation, and that "Settings" really is
translated in every locale. It runs as part of `build-translations.sh` and can be called on its own:

```bash
php tests/check-translations.php
```

`tests/check-i18n-bootstrap.php` covers the wiring instead of the strings: it stubs the handful of
WordPress functions the plugin calls while loading, requires the main plugin file and asserts that
`load_plugin_textdomain()` points at this plugin's `languages/` folder, that `plugin_locale` maps
`pt-BR`/`es-MX`/`fr-FR`/`zh-CN`/`hi-IN`/`en_GB`/`ar_SA` as documented above, and that
`is_rtl_locale()`, `language_attributes`, `admin_body_class` and `login_body_class` only change
right-to-left output.

```bash
php tests/check-i18n-bootstrap.php
```

Runtime smoke test without WordPress — the compiled catalogs are plain GNU gettext files:

```bash
python3 - <<'PY'
import gettext
for locale in ['pt_BR', 'es_MX', 'fr_FR', 'zh_CN', 'hi_IN', 'ar']:
    with open(f'languages/icc-gg-sign-in-openid-connect-{locale}.mo', 'rb') as handle:
        print(locale, gettext.GNUTranslations(handle).gettext('Settings'))
PY
```

In WordPress, switch the site or profile language and reload **Settings → OpenID Connect** and the
login screen; for Arabic the page must be mirrored (`dir="rtl"`, `rtl` body class), the discovery
form's accent border must sit on the right and the login button logo must sit to the right of the
text.

## Release packaging

`.github/workflows/build.yml` packages the release with `zip -r … .`, and
`.github/workflows/wordpress-deploy.yml` copies the tree with `rsync`, so `languages/` ships
automatically; no workflow change is needed when catalogs are added. `.dockerignore` only keeps
`docs/`, `plans/`, `docker/` and `.github/` out of Docker build contexts — it does not affect the
ZIP. Verify a release archive with:

```bash
unzip -Z1 icc-gg-sign-in-openid-connect.zip | grep '^icc-gg-sign-in-openid-connect/languages/'
```
